```md
Irreversible OTP means one-time programmable hardware memory in the Pi can be written once, then not erased or rewritten.

For your case:
- Generating the device key with rpi-fw-crypto genkey --key-id 1 --alg ec writes key slot 1 permanently.
- That does not brick the device by itself.
- It means that specific key slot is fixed forever, so you cannot rotate or replace that key later.

So, is the whole device locked?
- Not fully locked just from that step.
- It becomes locked to that key identity for features using that slot (your TLS/device cert flow).
- You can still boot and use the system normally.

The operations that can lock you out of boot/debug are different OTP actions, like:
- Permanently enforcing secure boot with fused public key/hash.
- Blowing debug/JTAG lock fuses.

Practical rule:
- Safe enough for intended production identity binding.
- Dangerous only if you provision before finalizing your key-management and secure-boot plan.
```

```md
Changing the SD card does not change the OTP data inside the Raspberry Pi chip.

What stays the same:
- The device key burned in OTP stays on the board forever.
- Any OTP fuse state (for example secure boot or debug lock fuses) also stays the same.

What changes with a new SD card:
- Files on disk are new, so generated cert files are gone until recreated.
- On first boot, the certificate service should generate a new rpi-device-cert.pem from the same OTP key, if that software is present and working.
- Hostname, IP, and other OS-level identity details can change, so the new certificate contents may differ even though the hardware key is the same.

Boot behavior by security state:
- If secure boot is not permanently fused, most compatible images can still boot.
- If secure boot is permanently fused, only SD images signed by the enrolled boot key will boot.

So the board is not “reset” by swapping SD cards; hardware trust state remains tied to the board.
```
